# Runtime extraction evidence

Issue #3 covers the complete dataset and mechanics. The tools here capture evidence from the released pack; they do not yet produce a complete planner dataset.

## Reference inputs

The CurseForge 2.0.1 client archive and the GitHub 2.0.1 client release have identical SHA-256 hashes: `7c39a9cd56b52e320fdfdb72300bc3317f51bf02feaec0a358a46f3123deaa4d`. The GitHub server archive is `7bf868078e1c403b1a264baeafab8c5e443f2ffbc33484347438fc894e45ce8f`. The manifest specifies Minecraft 1.21.1 and NeoForge 21.1.250. `data/provenance/sources.json` records archive and source revision identities. `statech-2.0.1-inputs.json` records every released server mod archive, declared version and license, and every pack script and configuration input hash.

The release contains MI 2.5.8, EI 1.16.2, IO 1.14.0, YAI 1.6.3, MI Tweaks 1.9.5, Tesseract API 1.12.16, StaTech Companion 1.0.3, and AE2 19.2.17. Source checkouts are pinned; the IO and YAI source heads declare the matching versions but still need bytecode comparisons for each calculation rule used.

## Reproduce the capture

Keep downloads and worlds outside the repository, such as `F:/sti2-work`. Download the client and server archives from the recorded release, unpack both, and make a separate working copy of the server. Install Java 21 and NeoForge 21.1.250 in that working copy using the official installer. Bind the test server to localhost. Do not use a player's existing world for instrumentation.

Run `python tools/extraction/inventory.py --server <unmodified-server-directory> --client <unmodified-client-directory> --output <inventory.json>` before modifying the instance. The output must match the pinned inventory.

Copy `tools/extraction/runtime_export.js` to the isolated instance's `kubejs/server_scripts/zz_planner_export.js`. Run `python tools/extraction/build_probe.py --instance <instance> --jdk <jdk-directory> --work <private-build-directory>`, then copy the resulting `planner-probe.jar` into the instance's `mods` folder. Restart the server after changing the Java probe.

After startup and all runtime recipe injection have finished, run `planner_export` and `planner_probe` in the server console. KubeJS script changes require `reload` before running the export again. Read `planner-extraction/runtime.json` and `planner-extraction/machines.json`. A success line is not sufficient: inspect the failure arrays, expected counts, and arithmetic samples. Keep the complete console log privately to distinguish pack warnings from extraction failures.

For a prepared Windows instance, `python tools/extraction/run_capture.py --instance <instance> --jdk <jdk-directory>` starts the server, waits for startup, runs both commands, and stops it. Run `python tools/extraction/verify_capture.py --capture <instance>/planner-extraction --output <report.json>` to validate the pinned counts, tag membership, array eligibility, and arithmetic. Use `--compare <previous-runtime.json>` to require a repeated capture to have identical content after canonical ordering. The compact report records actual loaded mod versions, including nested dependencies. Run the extraction regression checks with `python -m unittest discover -s tools/extraction -p 'test_*.py'`.

The recipe export reads both the recipe manager and every MI machine recipe provider. The latter supplies thousands of recipes absent from the manager, including generated canning and proxied smelting recipes. Recipe identity includes recipe type and ID because proxy recipes can share an ID with their source recipe. The TaCZ adapter records resolved ingredients and output components when that mod's serializer cannot encode its runtime recipe.

The machine probe creates detached block entities in the loaded server context and reads their actual components, capacities, batch limits, array eligibility, and serialized NBT. These are configuration probes, not functioning world machines. Batch energy probes use a known operation energy and the loaded transform. Arithmetic samples invoke the actual MI crafter method. Physical multiblock formation, throughput, and full warm-up behavior still require controlled world tests.

## Calculation findings

MI's base singleblock electric limit is 32 EU/t and its base overclock rate is 8 EU/t. Upgrades add to the limit. For a recipe with total energy E, recipe EU/t R, base B, maximum M, and efficiency counter e, the source computes `min(E, M, max(B, R) + floor(e * E / 600))`. The efficiency counter increases on completed recipes, not on every elapsed tick. The last tick consumes only the remaining energy. A planner must use whole ticks and the completion recurrence when estimating warm-up.

Tesseract's batching crafter transforms energy and base limits with the batch multiplier and discount, while adding upgrade energy separately. It casts floating-point transformed values to integers. Applying singleblock upgrade behavior independently to every internal machine would be wrong. The loaded Large Scale Assembler reports batch size 16, base 8 EU/t, base maximum 32 EU/t, and a 1,000,000 EU probe transforms to 13,600,000 EU for its full batch.

The two processing arrays accept different machine classes. The singleblock array accepts eligible electric singleblock machines; the multi-processing array accepts eligible MI electric multiblocks. Batching replacement machines do not automatically qualify for either. A controlled attempt to put the Large Scale Assembler into a multi-processing array was rejected by the actual mod class cast; do not expose that combination as valid.

The loaded MI Tweaks configuration has constant-efficiency hacks and casing-based overclock overrides disabled. Its redstone lock option is also disabled. Record these settings alongside extracted rules rather than assuming upstream defaults.

The machine probe also records primitive component fields and evaluates each loaded generator's fuel acceptance against the item and fluid registries. The fuel map's own enumeration method is unavailable for dynamic fluid fuels, so registry enumeration must call `accept` and `getEuProduction`. There are 12 captured generator configurations. The LV diesel generator supplies up to 64 EU/t and converts diesel at 800 EU/mB after its loaded multiplier; the large steam turbine supplies up to 16,384 EU/t and accepts four steam variants. The compact report retains the full verified fuel mappings. The bronze and steel boiler adapters include their loaded heater and solid-fuel rules. Other generator families still need their own process adapters.

## Remaining verification

The boiler probe runs the real heater and fuel-burning components in their normal tick order, records each change in steam output, and retains coal, water, steam, and cold-start deficit totals. The JavaScript boiler adapter matches every segment for both tested machines. This is a detached component test with continuous supplies and drained outputs, not a formed multiblock throughput test.

`python tools/extraction/normalize.py --capture <capture-directory> --output <private-output.json>` produces an intermediate capture format with version 1. It retains every source recipe, resolves item and fluid tag alternatives, preserves catalyst probabilities and process conditions, and reports unsupported ingredient and process adapters. The current reference capture yields 17,148 normalized processes and 9,333 explicitly unsupported entries. All 10,024 MI-style processes normalize. Component-bearing resources have stable identities; component predicates retain their captured matching display variants and the predicate itself. Those display variants do not establish every possible matching component combination. A normalized process is not a verified machine allocation: recipe-specific remainders, automation capacity, conditions, and machine-specific adapters must still be supplied. Keep this intermediate output private until the bundled dataset's redistribution audit and final format are complete.

The Java probe calls the loaded replication predicate, burn-time method, and crafting-remainder method for 11,573 default item stacks. It also decodes 202 distinct custom ingredient records through the loaded ingredient codec and verifies that each displayed stack satisfies its predicate. Both probes have zero failures. Default item metadata does not establish behavior for arbitrary component variants or recipe-specific remainder overrides. Loaded power conversion is 10 FE per EU and 2 FE per AE, with AE usage multiplier 1. The matching AE2 molecular assembler code ticks every game tick, has five acceleration-card slots, and charges the full final processing tick; its capacity evaluator includes that rounding.

The crafting probe inspects 7,301 loaded shaped and shapeless recipes. It tests a displayed ingredient combination, calls the actual assembly and remainder methods, and records the implementing class. Forty-six recipes need extra state or return an empty result with that combination; they remain explicitly unavailable. The iron-hammer plate recipe returns a hammer with 50 damage. Cake returns its three buckets. KubeJS's matching bytecode delegates ordinary remainders to the input stack when no ingredient action applies. The compiler permits the standard vanilla and KubeJS classes with unchanged results and no scripted ingredient action; component variants and tool damage still require separate adapters.

Run `python tools/extraction/player_dataset.py --input <normalized.json> --output <private-catalog.json>` to build the portable development catalog. It currently contains 28,558 process records and 9,333 separate unsupported source records. It supplies MI process rules, ordinary crafting through AE2, captured buffered generator fuels, bronze and steel boilers, and all three MI water pumps. `node tools/verify_real_catalog.mjs <private-catalog.json>` checks actual copper-cluster maceration, cake remainders, and the boiler/pump steam feedback through the shared solver. This catalog is still incomplete and private pending the full mechanics and redistribution audit.

A fresh-start repeated capture passed canonical comparison for all 26,481 recipes, resources, tags, and data maps. Both capture files had empty failure lists, and the machine report contained 211 entries. `data/provenance/runtime-report.json` records the counts, content digest, loaded mod versions, and arithmetic samples. The reference server emits unrelated optional-mod recipe warnings during startup and a configuration-unload exception during shutdown; the completed capture and its validation are separate from those pack log messages.

This capture does not establish full dataset coverage, redistribution approval for arbitrary mod assets, normalized process adapters, generation and closed-loop rules, complete upgrade compatibility, recipe conditions, warm-up buffers, or real-save reconstruction. No textures, mod jars, or worlds belong in the repository. Keep all unsupported recipe types and mechanics visible in the eventual dataset coverage report.

The water-pump probe temporarily places each actual pump in an empty area of the private test world and restores that area afterward. Bronze, steel, and electric pumps produce 1,000, 2,000, and 16,000 mB respectively every 100 ticks with eight counted water sources. Each consumes one unit of steam or EU per tick. A diagonal source counts only when an adjacent cardinal source exists; the probe verifies empty, isolated diagonal, paired, and full neighborhoods. The catalog exposes one through eight sources as explicit environmental configurations. Boiler startup stocks reserve actual cold-start fuel and water and the steam delivery deficit at the selected demand. These reserves include the initial water needed to bootstrap a steam-powered pump. Creative blaze cake cannot fuel a route until explicitly marked obtained.

The replicator tick probe produced one iron ingot on ticks 20, 40, and 60, consumed 300 mB of UU matter in total, and retained its one-item template. The catalog adds 11,257 default-stack replication routes accepted by the loaded predicate. Each is disabled in replicatorless mode and requires an obtained template plus one retained template per machine. Automatic planning of template acquisition is still pending; arbitrary component variants are not implied by default-stack checks.

Loaded large-electric-furnace coil tiers allow batches of 16, 32, and 64 at a 0.75 energy multiplier. Loaded pyrolyse tiers allow 1, 4, and 8 at multipliers 0.9, 0.8, and 0.75. Configuration validation applies the selected tier before batching and energy calculations. The tungstensteel furnace tier is a pack addition and is read from the loaded tier registry.

The dragon-egg siphon probe sets each loaded recipe on the actual crafter and calls its completion behavior against an energy output component. The two pack recipes release 102,400 and 204,800 EU, each after 100 internal progress ticks. Internal progress consumes no supplied electricity. The condition accepts an empty output buffer and rejects a full one. The adapter requires a single output hatch that can accept the complete burst; it also retains the fluid coproduct and the structure's dragon egg in the build requirements. Actual crafter ticks also verify both complete siphon cycles, including consumed inputs and fluid outputs. These are component checks with supplied inventories, not formed multiblock throughput tests. The pack removes arboreous-greenhouse recipes in its scripts, so the absence of that family in the effective recipe capture is expected.

The custom ingredient probe evaluates all 202 predicates against 12,319 candidate item stacks: default items, displayed ingredient variants, and component-bearing stacks encoded in effective recipes. It records 752 component-variant remainder samples. The catalogue uses only positively matched variants and labels the untested space of other component combinations. This enables the previously excluded component ingredient routes without assuming that display lists are exhaustive.

The loaded iron-plate hammer recipe consumes four ingots per plate. Repeated actual recipe remainder calls break iron, steel, diamond, and netherite hammers after 34, 87, 209, and 271 crafts. The probe also decodes each actual AE2 pattern and verifies that every damaged hammer remains valid with substitutions enabled. Separate tool-specific routes retain one working tool per assembler and amortize replacements over that lifetime. Enchanted tools and finite-job rounding are not implied by this steady-state rate.

All four MI large boilers now have cold-start schedules and a hot-running probe for every integer steam output from zero to full capacity. The probe calls the loaded heater and burner against constrained output slots, then reads the actual fuel-energy buffer change. The ordinary large boiler retains 205 EU/t of fuel use at zero output and reaches 256 EU/t at full output. High-pressure variants use eight EU per mB of steam. The catalog uses efficient periodic dispatch points with explicit buffering assumptions and accounts for fixed hot losses at partial load. Cold-start steam, water, fuel, and delivery deficits match the loaded components for all six boilers. Boiler routes include item fuel, loaded fluid fuels that fit the actual refill buffer, and ordinary or heavy-water variants at either supported pressure. Diesel-fueled heavy-water startup schedules also match all six loaded boilers. Fluid fuel keeps its own EU per mB and does not receive the item-fuel multiplier. These component checks do not establish formed-structure hatch capacity.

The pulse detonation generator uses the same verified burst-generation family. The probe runs all eight actual crafting cycles with their recipe inputs and an empty output-energy component. Completion ticks, consumed inputs, fluid coproducts, and energy match the loaded recipes, including the 24.576-billion-EU burst from the 64-nuke recipe. The calculator includes the fuel chains and reserves the full burst as startup energy stock when sustaining its average output from a cold start. A single output hatch must accept the entire burst; this avoids assuming that the mod's multiple-hatch insertion code distributes it correctly. Structural build bills and a formed-machine throughput check remain separate work.

The progression extractor reads the eight released FTB Quests chapter files through the loaded FTB Library SNBT parser. It records chapter IDs, file paths, and item-task IDs without treating quest rewards or icons as unlocks. Presets use cumulative item tasks and verified crafting conversions from already listed machines. Their source metadata records those conversions. Files are already covered by the extraction input hashes. The Electrical age preset includes the molecular assembler and basic MI upgrades; both processing-array types first appear in Quantum age. Unlisted entries remain available through individual overrides or the all-supported preset.

Initial graph categories are display hints derived from process types and resource names. They include extraction, ore processing, metals, chemicals, fuels, circuits, machinery, and power. These categories do not change recipe eligibility, costs, or calculations, and players can edit their workspace groups.

The probe reads both single shape templates and template arrays. This includes the four large boilers, whose structures contain 35 or 44 template cells before the controller. It records each hatch's empty slot capacities, fluid volume, energy buffer, and cable tier from the loaded objects. Examples include 15 slots in the highly advanced item hatch, 1,024,000 mB in its fluid counterpart, and 76,800,000,000 EU in a superconductor energy hatch. These are storage and cable-tier facts; transfer networks and a complete structural bill still need to be considered separately.
