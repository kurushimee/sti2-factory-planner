# Planning kernel

Issue #5 owns this implementation. The Godot workspace uses the kernel on desktop and web. Integration with the complete StaTech dataset remains in progress.

`kernel/planner.js` builds a mixed-integer model for operation rates, whole-machine allocations, explicit external supplies, and resource balances. Generation is represented as a process producing `energy:eu`; production and generation support processes consume that same resource. Fixed infrastructure demand is included in the energy balance. Positive allocation costs prevent unused machines from being added for free.

Graph flow allocation uses compensated sums when sharing a source among many consumers. Any remaining floating-point shortfall uses one numerical budget for the entire resource, consistent with the resource-balance check; it does not receive a new allowance at each consumer. Results record accepted shortfalls in `flow_roundoff`, with the resource, omitted rate, and tolerance. Deficits above that budget remain errors. The large-flow fixture retains a 493-line StaTech candidate with more than 500 million EU/s of transfers. It checks numerical allocation only; its primary-route policy and global optimality are not established.

The default objective weights are 1,000 per external resource unit per second, 1 per machine build-cost unit, and 0.000001 per operating EU per second. These are configurable optimization weights, not claims about comparable real-world resource value. Recipe input costs include the complete connected support graph. Without construction accounting, build-cost values come from configuration records. Construction accounting adds the actual machine and upgrade recipe chains; enabling it by default remains pending.

An optional `request.construction` adds a separate material balance for installed controllers, upgrades, contained machines, and sized structures. Construction recipes share coproducts and return the selected containers. Their quantities never become sustained production rates. The primary-route rule, replication setting, available machines, recipe exclusions, and ingredient selections apply to this balance too. A configuration without a known bill is excluded with a reason; unresolved multiblock ingredients require a selection before this comparison. Different build bills remain available during configuration pruning.

This mode estimates material equivalents using continuous construction operation quantities and the loaded recipe amounts. Its optional `round_batches` setting instead requires whole recipe batches, purchased item quantities, and verified consumable tools. Tool uses are shared across sequential construction recipes with the same tool and verified lifetime; results report whole tools and remaining uses. A 35-plate job using the captured iron-hammer recipe needs 140 iron ingots and two hammers, with 33 crafts left on the second hammer. Probabilistic yields still represent expectations. Neither mode establishes workstation acquisition, initial catalysts, or loop fills. Construction work is summed full-speed machine time, not elapsed time. These assumptions are returned with the quantities and cost breakdown. Enable the estimate in Factory settings under Construction costs and select separately priced construction supplies. It is not enabled by default and still needs complete startup accounting and full-catalog performance checks.

Run `node tools/verify_construction_catalog.mjs` for the captured upgrade comparison. At 12 copper dust/s, the tested electric macerator needs four basic upgrades: each adds 2 EU/t, raising 32 to 40 EU/t so the 400-EU operation finishes in 10 ticks. The loaded assembly recipe produces four upgrades from two conveyors, four motors, two robot arms, and one analog circuit board. With those supplied components priced at one each and a macerator priced at 100, one upgraded macerator costs 109 material units. The test compares it with two unupgraded macerators and a quantum upgrade, whose actual ingredients are costed separately. This is an isolated component-price example, not a claim that these prices describe every playthrough.

By default, each active recipe owns one useful net output, and each resource has one primary owner. Other outputs remain available as coproducts. The dataset's `primary` field selects a display and goal default; it does not decide exclusive route ownership. This lets chloroform and tetrafluoroethylene production coexist even though the released recipes both list hydrochloric acid first. Explicit recipe goals can retain separate production setups, and power generation can combine methods. Resource pins restrict ownership while allowing supplies from other recipes' coproducts.

Small models use integer subproblems. If the unrestricted optimum already satisfies route ownership, it is also an optimum under that policy. Conflicting single-output routes can be separated exhaustively. Repairs involving several outputs are marked incomplete because a later consumer could make a previously unused coproduct useful. Those searches return `feasible` rather than falsely claiming an optimum or proven infeasibility.

Models with more than 2,000 configurations and no construction balance first solve a continuous relaxation, reuse its basis while repairing route conflicts, and recheck rounded machine counts in the original resource model. This is a heuristic; it does not prove the cheapest factory. The result reports the original relaxation's lower bound, the candidate's weighted objective, and the remaining relative gap. The native creative-storage-unit case at one item per hour took about 28 seconds including preparation and final checks, with 487 allocations. All native models are disposed after use, including failures. Returned plans still pass whole-count, capacity, resource-balance, flow-allocation, and route-ownership checks. Ingredient alternatives share the connected resource balance. The player can pin a slot through `ingredients["recipe_id#slot_index"]`. Results retain the actual selected ingredient rates. Goal types are `rate`, `capacity`, and `quantity`: capacity multiplies whole machines, operations per second, and the recipe's output amount; quantity reports production time at the specified rate after startup. Conflicting recipe or configuration selections produce an error.

Generation settings include installed counts, count limits, operation-rate dispatch bounds, and a reserve fraction. Reserve sizes installed generating capacity against all modeled consumption, including fuel support. It does not burn extra fuel merely to hold idle capacity. Standby fuel and startup stock still require separate calculations. External power counts toward reserve only when the player supplies its firm capacity, in EU per second. Results separate generated power, installed capacity, consumption, fixed demand, and margins.

`kernel/periodic_power.js` contains a fixed-profile, lossless storage balance for period-aware generation. It checks each tick's charge and discharge limits, total energy over the period, and the largest deficit across any interval that wraps around the period. A bounded-store replay confirms the minimum initial charge and reports curtailed output. Small hand-calculated cases and an independent exhaustive four-tick state search test the arithmetic. `kernel/solar_profile.js` reproduces the matching Extended Industrialization clear-sky curve and cell-expiry gap under continuous replacement. These are isolated primitives; the production optimizer, catalog, graph, and exported applications do not yet use them. Solar remains unsupported as a continuous generation choice until those integrations and weather assumptions are verified.

`minimumStorageCount` finds the smallest whole count of one chosen lossless storage tier for a fixed generation and demand profile. It scales capacity and both transfer limits together, checks every candidate with the full periodic balance, and returns an explicit failure under an installed-count limit. A measured LV panel at 14 EU/t for one clear day needs one measured LV storage unit; a restricted zero-unit case fails. This is a fixed-profile calculation, not a material-cost choice among tiers or a connected factory optimization.

The returned plan describes a steady-state balance. It does not yet establish bootstrap stock, a complete warm-up buffer plan, progression, recipe conditions, catalysts, or safe stochastic stock levels. A circulating container can balance at zero net consumption while still needing an initial fill; callers must not present the current result as a verified startup plan. These missing adapters and calculations remain required under #3 and #5.

## Capacity rules

`kernel/catalog.js` compiles configurations from the portable machine and process records. It follows every producer of a needed resource, including coproduct suppliers, and then follows their inputs and power requirements. Available-machine and upgrade lists constrain the generated loadouts. Every permitted upgrade count and batch size is considered. Arrays enumerate contained counts and supported shapes when enabled. Equal steady-state capacity and operating inputs can share the cheaper build option; explicit choices and installed constraints preserve alternatives. Startup and full construction costs are not part of this dominance comparison yet.

Ingredient flows may include `returns`, keyed by the chosen input resource. Each returned amount is per consumed input unit. The model ties that output to the actual ingredient-choice variable, so choosing one container cannot create another container's remainder. Results and graph flows include these returned materials.

`kernel/capacity.js` implements the independently captured MI crafter power samples and the Tesseract percentage-batching transform. Capacities use whole ticks. Upgrade compatibility and count limits are checked against supplied machine records. Batching transforms use Java float rounding before the integer cast, matching the source's arithmetic. Efficiency increases once per completed operation or batch. The output buffer calculation includes delivery before the first completed recipe, including machines without a warm-up phase.

The MI evaluator assumes continuous ingredients, space for outputs, and no overdrive or lubricant. Its ordinary and batching mechanics are named `mi_crafter` and `mi_batch`. Applying them to generators, alternate efficiency hooks, steam catalysts, or a different addon without an adapter is an error. The computed per-machine output deficit is not itself a whole-factory buffer schedule.

The additional `mi_array` adapter uses captured shape limits and contained-machine eligibility. Batching uses the array's own base and maximum power; it does not multiply the contained machine's upgrades. The `ae_molecular_assembler` adapter implements the matching AE2 acceleration-card steps and full final-tick power charge. `kernel/configuration.js` turns these calculations into concrete controller, contained-machine, casing, and upgrade counts. These are core configuration parts; full multiblock construction bills still need shape and hatch selection. Steam configurations consume a fluid resource separately from EU. Coil tiers and tower output levels constrain the available setup, and steam multiblocks can select the captured steel-hatch tier.

Capacity goals can preserve several loadouts for the same recipe. Each requested loadout has a minimum operation rate, so byproducts cannot silently remove a selected recipe goal. Independent requested outputs remain separate from downstream consumption. Goals for several coproducts share the same operations.

`kernel/startup.js` provides a conservative bound for one cold start where a verified completion schedule is available. It reserves all input operations through the first full-speed completion, plus output stock covering the producer's delivery deficit. It deliberately does not credit incoming startup production against those reserves. Results keep first loads, remaining warm-up inputs, reusable stock, and output deficits separate. This is not a minimum-stock schedule, a stochastic service guarantee, or a solution for repeated passive restarts. Missing schedules remain explicit, and `steady_state_only` remains true until bootstrap and full scheduling are established.

## Runtime and numeric behavior

`kernel/boiler.js` follows the loaded bronze and steel boiler heater and fuel-buffer tick order. Its cold-start output segments match direct calls to the actual loaded components with continuous coal and water supply. The bronze boiler first reaches full output on tick 3,906; the steel boiler does so on tick 2,417. The probe drains steam each tick so backpressure does not affect these measurements. Selected boiler schedules contribute fuel, water, and steam deficits to the conservative startup stock report.

Configuration searches can defer completion schedules with `compute_warmup: false`. The selected allocations reconstruct their schedules before startup stock calculation. This avoids allocating long completion arrays for unused candidate configurations.

The same HiGHS 1.15.3 WebAssembly runtime executes the model in Node and in a browser Worker. `kernel/desktop.js` accepts input and output file paths and publishes a complete JSON result through a temporary file and rename. The Windows development package bundles Node. `kernel/worker.js` uses local web assets and phase messages. Both adapters connect to Godot through `ui/computation.gd`; cancelling terminates the process or Worker.

Inputs outside JavaScript's safe integer range are rejected where integer arithmetic is required. Resource balances and whole-machine capacities are checked after solving. Results report each resource balance's numerical tolerance. Large coefficients and near-degenerate models still need broader endgame validation; the trillion-unit regression case is a focused check, not that validation.

Automatic array searches omit extra contained machines above the selected batch count: they add build cost without increasing capacity. Explicit setups and constrained configuration IDs remain available. Identical capacity and operating-cost configurations keep the cheapest unconstrained choice alongside pinned or constrained choices. `kernel/structure_bill.js` sizes ordinary MI item, fluid, and energy hatches for selected recipe batches and assigns them to captured allowed positions. Hatches replace casing cells. Item stack limits, fluid volumes, peak input power, and full-burst output buffers come from the captured dataset. A bipartite matching check prevents two hatches from claiming the same cell. The current choice minimizes hatch count and then prefers lower capacities; it does not include hatch material costs or progression availability in the optimization. Unverified predicates, unknown stack limits, unsupported utility demand, and structures that cannot fit the required hatches produce explicit incomplete reports.

The controlled steel-line bill was placed in the isolated loaded pack and accepted by its actual shape matcher: one controller, 14 heatproof casings, 16 cupronickel coils, one steel item input hatch, one bronze item output hatch, and one MV energy input hatch. This confirms geometry and the selected bill. It does not establish an observed sustained factory rate or verify the external transport network. Run `node tools/prepare_structure_fixture.mjs <catalog.json> <instance>/planner-structure-bill.json`, then the extraction runner with `--structure-bill`, to repeat that check in the isolated test world.

Boiler bills reserve hatch space for a whole tick of water and steam and the captured fuel-buffer refill. Buffered fuel generators reserve one production tick of fuel and output energy; the internal fuel buffer does not require an energy hatch large enough for a whole fuel unit. The real-catalog check covers all four large boilers with item and fluid fuels and all four supported buffered generator multiblocks at full power. These are calculated bills, not new formed-world throughput measurements.

Fixed-input configurations now check structural capacity before they enter optimization or capacity-cost pruning. `request.available_parts` can restrict hatch IDs. Unknown structure predicates remain visible as missing evidence; they are not treated as proof that a machine cannot be built. Unresolved ingredient alternatives still receive their actual storage report after solving and need further integration. Build reports are cached by shape and hatch-capacity choices within a single dataset request. The creative-storage-unit preparation benchmark takes about 3.2 seconds with these checks; this measures configuration preparation, not a solved endgame factory.

The irradiation adapter adds 30 fuel/source routes with one to eight nuclear hatches per controller. Each hatch holds one fuel rod; the operation rate counts rods rather than depleted output items. It preserves ongoing source use and power when an enabled machine runs below capacity. Beryllium use is an expected rate of 0.005 blocks/s with a continuously supplied stack and 1,024 EU/t. A demon core lasts 800 seconds of enabled time and averages 8,191.488 EU/t because its exhaustion tick is uncharged. Its peak remains 8,192 EU/t. All rod input and depleted output quantities come from the loaded fuel definitions.

A controlled eight-hatch irradiator at (192, 100, 0) accepted the planned geometry and completed eight uranium rods on tick 8,059, using 8,192,000 EU. The power report separates gross generation, generator and fuel-chain consumption, net generation, external supply, other production, infrastructure and power goals, running margin, and installed reserve. Generation support follows solved material connections upstream from generators, excludes electrical connections, and counts each allocation once. A shared supplier is counted in full in the generation-support category; this is an explicit attribution rule, not a marginal fuel-cost calculation. The workspace Power details button opens this report without moving the graph.

Construction orders can also be solved after selecting a factory. `kernel/construction_order.js` accepts enabled, configured workstation routes and a fixed bill of parts, then balances their complete construction recipes. It keeps supply quantities, alternative ingredients, returned containers, generation fuel, and whole-batch tool lifetimes. It does not require buying every candidate workstation. As with the joint construction model, those workstations and reusable catalysts must already be available. Large construction requests use this stage to compare endgame loadouts.

For identical material flows and batch constraints, construction preparation drops a workstation only when another has no greater objective cost or energy use. It retains slower choices that save energy. Sustained production configurations are unaffected by this construction-only reduction.

For a solved continuous construction order, the kernel also returns marginal resource costs from the LP dual solution. These describe the current order and enabled workstations; they are not fixed market prices or a proof that a later machine choice is optimal. Whole-batch orders do not expose continuous marginal costs. A candidate factory still needs its own construction balance check.

Fixed construction orders check route ownership together with the supplied sustained factory. Recipes whose only possible useful output already belongs to an unavoidable sustained recipe can be excluded before solving. Other conflicts use a persistent solver search, preserve production and pinned routes, and report a feasible result without claiming a global optimum. Returned containers can give a recipe another useful purpose; mixed primary routes remain available when explicitly enabled.

Solver feasibility alone does not accept a plan. Production and construction flows are independently recomputed in resource units. The absolute numerical allowance is capped for small flows so it cannot erase a tiny demand. Zero machines cannot provide positive capacity. Decoding retains every positive input, output, construction quantity, and route contribution.

A rejected result receives a bounded numerical retry. Production can rescale constraint rows while leaving variable units, integer counts, and the objective unchanged. Construction can restore and rescale a failing row, including coefficients the solver parser discarded as too small, or retry without presolve and matrix scaling. Construction marginal costs are converted back to the original resource units. These row-recovery results do not claim an optimal cost or a global bound. If balances still fail, the application reports a numerical error and preserves the previous graph.

Large construction requests use a bounded material-cost search once preparation exceeds 5,000 configuration attempts or retains more than 2,000 configurations. The kernel first verifies a sustained production plan, then solves its complete fixed construction order. Marginal prices from that order first rank alternative loadouts for the active recipes. A second pass considers reachable alternative recipes, keeping their ordinary capacity frontier to bound the search. Each pass solves the connected production model again and gives its candidate a new complete construction order. It replaces the baseline only if its actual combined cost is lower. A failed candidate or exhausted budget preserves the last verified plan. If no complete baseline construction order exists, the request returns no new plan.

This search preserves goals, explicit choices, availability, and combined production/construction route ownership. It compares a limited set of loadouts and routes, so it reports a feasible result without a global bound. Per-pass records show the candidate counts, whether a complete candidate was verified, and whether it improved the plan. It does not establish the acquisition of reusable construction workstations. Small construction models retain joint integer optimization. Construction requests have a default 180-second budget; an explicit `time_limit_ms` still takes precedence.

Construction decoding also checks alternative-ingredient equations independently of resource rows. A scaled numerical retry disables presolve as well as matrix scaling. Values are not clamped to zero to make a result pass.

Dataset route preferences remove an equivalent-material alternative only while its preferred route has an available, unconstrained configuration. Explicit recipe goals, route pins, configuration pins, and installed or limited alternatives are preserved. The preferred set receives 90% of the remaining solve budget; an unsuccessful search retries the full set and labels the fallback. The player can disable the policy in factory settings. Selected nodes explain applied choices. These preferences are part of the chosen optimization policy, not a claim that the preferred route has lower power or construction costs. `tools/test_recipe_preferences.gd` checks the real route's inspector; `node tools/verify_endgame_browser.mjs --preferences` checks exported browser calculation, exact plan export, persistence, and reload.
